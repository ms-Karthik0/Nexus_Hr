01 · Product brief

Project overview

02 / 15

NexusHR brings daily workforce operations into one role-aware application: a React client, Spring Boot REST services, and relational persistence with a lightweight local-development profile.

Vision and objectives

Vision

Reduce context switching across people operations by bringing employee records, attendance, leave, payroll, reviews, notifications, and workforce insights into a coherent workspace.

Product objectives

  • Digitize lifecycle and approval workflows.
  • Make payroll calculations and employee-facing payslips accessible.
  • Support role-specific workspaces and self-service actions.
  • Present workforce-risk signals with factors and suggested interventions.

What “AI” means in this implementation

Explainable rules, not a trained model. The inspected service computes risk using fixed rules for engagement, tenure, compensation and in-demand skills. A confidence value of 88.4 is assigned in source code; this is not evidence of benchmark validation or measured predictive accuracy.

Useful demo behavior

  • Risk score is capped to a bounded range.
  • Results are classified as low, medium or high.
  • Risk factors and interventions accompany each result.
  • Skill targets and current proficiency values produce gap bands.

Before operational use

  • Define a lawful, representative training and evaluation dataset.
  • Measure precision, recall, calibration and subgroup effects.
  • Document human review and contestability.
  • Review privacy, labor and employment-law obligations.

04 · System design

Architecture at a glance

06 / 15

A browser client calls a single Spring Boot API surface. Controllers delegate to domain services and repositories; the active profile selects the database configuration.

Request path

01 · Authenticate

Login endpoint

Credential check returns user identity and token data; the web client stores session details locally.

02 · Authorize

Security boundary

A JWT filter populates the security context; controller method annotations apply role rules.

03 · Persist

Domain service

Typed repositories and JPA entities implement persistence and business workflows.

Architecture boundaries to preserve

  • Keep role decisions server-enforced; client-side menu filtering is not a security boundary.
  • Keep the demo heuristic separate from any future trained-model inference service.
  • Externalize secrets and environment-specific origins before shared or public deployment.

06 · Engineering practices

Technical highlights · Security

08 / 15

The implementation contains foundational controls, but the project should be treated as an evaluation/demo application until a security review and deployment hardening are complete.

Control areaRepository evidencePractical assessment
IdentitySpring Security authentication manager; BCrypt password encoder; JWT access and refresh token paths.Present in code. Rotate secrets and add key management, token revocation/rotation policy and abuse controls.
AuthorizationMethod security enabled; controllers use @PreAuthorize for selected actions.Promising server-side boundary; audit every controller and every object-level ownership check.
Input handlingRequest DTOs and Jakarta validation are used on selected controller inputs; JPA repositories structure data access.Validate every endpoint and enforce business invariants at the service layer; test malformed and oversized inputs.
Transport / CORSCORS bean accepts wildcard origin patterns with credentials; application YAML also declares an origin list.Configuration mismatch / broad policy risk. Use a single explicit allowlist and verify effective browser policy.
CSRF / sessionsCSRF is disabled and Spring sessions are stateless.Appropriate only for a correctly managed bearer-token API; protect browser token storage and review XSS exposure.
SecretsJWT secret appears in application YAML; Compose includes a sample database password. K8s references a Secret for DB credentials.Do not reuse committed values. Rotate, remove from source control, and inject through a secret manager.
Abuse controlsNo rate-limiting implementation was identified in reviewed configuration.Add login throttling, request limits, account lockout policy and monitoring before exposure.
Logging / auditSecurity/audit UI and Prometheus scrape configuration exist in the project.Verify immutable event capture, sensitive-data redaction, retention and alert response. UI labels alone are not audit evidence.

OWASP-oriented threat checklist

Access and injection

  • Test horizontal and vertical privilege boundaries.
  • Verify resource ownership on reads and updates.
  • Prefer parameterized persistence; test validation and error paths.
  • Do not rely on hidden navigation to authorize API access.

Secrets and availability

  • Rotate demo and signing credentials before deployment.
  • Limit CORS to reviewed client origins.
  • Add login rate limits and security event alerts.
  • Use TLS, backups, restore drills and dependency scanning.
Public-demo warning. Demo credentials, H2 Console settings and any checked-in signing keys must be treated as unsafe for a public or shared deployment. Replace and rotate them first.

07 · Authentication experience

Role-based access and user journeys

10 / 15

The sign-in experience offers four account choices. A successful authentication should determine the account role; switching personas requires signing out and signing in with a different account.

RoleRepresentative journeyUI navigation availableServer checks
Executive AdminReview workforce overview → inspect payroll → audit controls.Dashboard, employees, attendance, leave, payroll, performance, AI, security.Controller-level authorization annotations apply to selected operations.
HR ManagerFind employee → review leave → check pay and retention indicators.HR operational modules and governance views.Role authority checked by backend where configured.
Team ManagerReview team attendance → approve leave → contribute performance feedback.Team-oriented modules; some admin-oriented views are hidden.Object ownership / team scoping should be tested for every endpoint.
EmployeeCheck personal time → submit leave → view payslip and review.Self-service modules and personal actions.Self-only record access must be enforced server-side.

Authentication path

Demo account handling

Evaluation accounts only. Accounts and passwords documented by the project are hard-coded sample credentials in demo setup. Do not publish or reuse them on a publicly reachable deployment; replace seeded passwords and rotate signing/database secrets.

When the API is unreachable, the frontend contains a demo-account fallback. That fallback is for local evaluation and is not an identity provider. A production release should fail closed, use a controlled identity service, and avoid storing bearer credentials in browser local storage.

Reflection and next steps

Engineering learnings

  • End-to-end role flows are easier to reason about when demo persona switching is replaced with authentication.
  • Targets should be documented separately from measured outcomes.
  • Security posture depends on effective configuration, not only framework defaults.

Roadmap

  1. External identity, key management, strict CORS and throttling.
  2. Persistent test database, API authorization tests and CI security scanning.
  3. Payroll jurisdiction review, audit retention and accessible UI tests.
  4. Reproducible performance plan; model evaluation and human governance.
  5. Production runbook, recovery test, alerting and real deployment evidence.
Closing note. NexusHR is a broad, visually demonstrable HR platform concept with a clear path from local prototype to a production-ready system—provided that identity, privacy, correctness, performance and operational controls are validated before real employee use.
